# 화면 사전 로딩과 번들 성능 예산 검증 요약

## 목적

관문 12-11에서 화면별 코드를 지연 청크로 분리한 뒤, 관문 12-12에서는 사용자가 다음 화면으로 이동하려는 의도를 보일 때에만 해당 코드 청크를 미리 받도록 보완했다. 초기 수주 화면의 기능과 데이터를 미리 전부 받아 두는 방식은 사용하지 않았다.

## 구현 결과

- `screenModules` 레지스트리가 React 지연 컴포넌트와 preload에 같은 importer와 Promise cache를 사용한다.
- 데스크톱 메뉴의 mouse enter, keyboard focus, pointer down에서 목적 화면 코드만 preload한다.
- 이미 받는 중이거나 받은 화면은 같은 Promise를 재사용하므로 같은 청크를 중복 요청하지 않는다.
- preload 실패는 cache를 비우고 현재 화면을 유지한다. 실제 이동 시에는 기존 Loading / Error / 다시 시도 경로가 계속 책임진다.
- 코드 preload는 업무 API를 호출하지 않는다. 수주 화면의 미저장 변경 보호는 기존 클릭 경로 그대로 유지된다.
- 현재 모바일·PDA 진입은 직접 URL/직접 진입 구조이므로, 별도 메뉴를 억지로 추가하지 않았다. 컴팩트 화면 자체는 하나의 지연 청크로 공유한다.

## 실제 번들 측정과 예산

복원된 생산 빌드에서 측정한 기준값은 다음과 같다.

| 항목 | 실제값 | 예산 | 결과 |
| --- | ---: | ---: | --- |
| 엔트리 raw | 273,634 B (267.22 KiB) | 315,000 B | PASS |
| 엔트리 gzip | 84,887 B (82.90 KiB) | 98,600 B | PASS |
| 초기 JS raw 합계 | 273,634 B | 315,000 B | PASS |
| 초기 JS gzip 합계 | 84,887 B | 98,600 B | PASS |
| 초기 비기본 화면 모듈 | 0 | 0 | PASS |
| 가장 큰 동적 청크 (AI 솔루션 센터) | 151,387 B (147.84 KiB) raw | 175,000 B 경고선 | INFO |

예산은 관문 12-12 기준값에 약 15%의 허용 범위를 둔 회귀 방지선이다. gzip 값은 Vite 표시값이 아니라 산출물 파일을 Node `gzipSync`로 다시 압축해 계산한다.

## 변이 검증

`PurchaseOrderRegistration`을 임시로 `App.tsx`에 정적 import한 뒤 생산 빌드와 예산 검사를 실행했다. 빌드는 의도대로 성공했지만, 초기 비기본 화면 모듈이 `1`이 되어 예산 검사에서 실패했다. 해당 임시 변경을 즉시 원복한 뒤 다시 빌드·검사하여 `0`으로 통과한 것을 확인했다. 이 검증은 정적 import 회귀를 빌드 성공만으로 놓치지 않는다는 근거다.

## 사용자 영향과 한계

다음 메뉴로 이동할 의도가 있을 때 코드 수신을 앞당겨 전환 체감을 줄이고, 첫 수주 진입은 필요한 화면만 받는다. 사전 로딩은 브라우저 네트워크 조건, 캐시 상태, 실제 고객 데이터와 같은 현장 조건을 측정하거나 보장하지 않는다. 운영망 체감 성능은 별도 환경에서 확인이 필요하다.
